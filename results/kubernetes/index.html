GuardScale · Local Kubernetes measurement

First cluster run

One seeded synthetic legitimate flash trace was replayed against a CPU-bound HTTP service in a two-node kind cluster. The host-side prototype changed the Kubernetes Deployment replica count and recorded client request latency and pod readiness.

Evidence limits: this is one seed and one synthetic scenario on a local Docker Desktop cluster. It is an exploratory systems measurement, not a statistically supported performance claim, an attack-detection result, or cloud cost evidence. The 2-second comparison uses each one-second window’s request p95.

How to read this

The offered trace is identical across policies (seed 1, 180 seconds, 20,548 requests). The current GuardScale decision policy uses more target replica-seconds than either baseline in this single run. Its worst window also has a latency spike. This is a negative result for the present configuration, not evidence of a benefit.

* Target replica-seconds are the sum of requested replica counts across trace windows. They are a workload-time resource proxy, not metered node time or a cloud invoice. Mean and median p95 columns summarize per-window p95 values; they are not the p95 of all requests pooled together.

The app performs 12,000 SHA-256 operations per request. CPU/memory limits, scenario, seed, and workload trace are recorded in the CSV and paired JSON summaries. The runner uses a host-side kubectl loop; it is not yet an in-cluster controller, KEDA integration, or production operator.
